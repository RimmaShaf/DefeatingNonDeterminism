Floating Point Non-Associativity

In math, (a + b) + c = a + (b + c). In floating point, it isn't — because every intermediate result must round back into a fixed number of bits.

FP16 — How bits become a number

IEEE 754 half precision: 1 sign · 5 exponent · 10 mantissa bits.

value = (−1)sign · 2E − 15 · 1.mantissa
E is the 5-bit exponent field read as an unsigned integer (0–31). The 15 is the bias — it shifts the range so E = 01111 means "no scaling" (20 = 1). That's why exact 1.0 has exponent bits 01111.

(big + 1) − big  ≠  (big − big) + 1

With big = 108, the value 1 is so much smaller it can't survive the addition — it rounds away. But subtract first, and it survives.
Using float32 here, because 108 overflows FP16's max of 65504.

The same hardware. The same three numbers. Only the order changed. This is why parallel reductions (where chunks combine in nondeterministic order) produce slightly different sums on every run.

Inside the adder — watch bits fall off the register

Floating-point addition can't just add two bit patterns. First it has to align the exponents — shift the smaller number's mantissa right until its exponent matches the larger one's. Anything that shifts past the register width is gone forever.
